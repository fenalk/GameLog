# Registro da Sessão — GameLog

**Data:** 05/10/2026
**Ferramenta:** Copilot (AI assistant using Copilot SDK in VS Code)
**Tema:** Planejamento geral (plan.md), proposta de tecnologias, backlog de tarefas (task.md) e SPEC de arquitetura da Etapa 0

---

## Usuário

Leia o arquivo docs/visao_geral.md do projeto GameLog. A partir exclusivamente das informações
presentes nesse arquivo, crie em .sdd/plan.md, contendo o planejamento geral do desenvolvimento
do sistema.

O plano deve:

- organizar o desenvolvimento em etapas;
- identificar as principais funcionalidades do sistema;
- estabelecer uma ordem lógica de implementação;
- ser compatível com o desenvolvimento utilizando SDD;
- não detalhar requisitos funcionais individuais, pois eles serão definidos posteriormente nas SPECs;
- não implementar código.

O plan.md deve funcionar como um roadmap geral do projeto, enquanto as SPECs serão responsáveis
por detalhar os requisitos de cada funcionalidade.

## Copilot

Li `docs/visao_geral.md` e criei `.sdd/plan.md` como roadmap geral do GameLog, baseado
exclusivamente na visão geral.

Conteúdo do plano:

- **Objetivo e escopo** — deixa explícito que o plano não detalha requisitos funcionais nem implementa código.
- **Papel dentro do SDD** — separa responsabilidades entre `plan.md` (roadmap), `SPEC/` (requisitos por funcionalidade), `src/`, `tests/` e `prompts/sessoes/`, além do fluxo *plan → SPEC → implementação → testes → registro da sessão*.
- **Contexto de partida** — problema, solução, personas e tecnologias iniciais.
- **Funcionalidades** — as 15 funcionalidades da visão geral, agrupadas em 5 domínios (usuários, catálogo, atividade do jogador, social, moderação/administração), sem detalhar cada uma.
- **Etapas (0 a 7)** — Fundação → Identidade e acesso → Catálogo → Atividade do jogador → Listas → Social → Moderação/administração → Consolidação.
- **Dependências e ordem lógica** — tabela de dependências entre etapas e justificativa da ordem `0 → 1 → 2 → 3 → 4 → 5 → 6 → 7`.
- **Critérios para avançar de etapa** e **práticas transversais** (incluindo o registro de sessões no formato `AAAA-MM-DD-HHMM-<ferramenta>.md` em `prompts/sessoes/`).

O documento é um roadmap: cada etapa apenas nomeia funcionalidades e sua posição na ordem de
implementação, remetendo o detalhamento às SPECs.

## Copilot

Antes de escrever, perguntei onde registrar a proposta. O usuário escolheu **criar um novo
arquivo `docs/tecnologias.md`**.

> Escolha do usuário: "Novo arquivo docs/tecnologias.md (Recomendado)"

Criei `docs/tecnologias.md` com a proposta ancorada no que a visão geral já fixa (Node.js,
TypeScript, banco relacional, Git/GitHub, API REST). Resumo das escolhas:

| Camada | Escolha | Motivo principal |
| --- | --- | --- |
| Runtime / linguagem | Node.js LTS + TypeScript `strict` | Já definidos; tipos como verificação dos requisitos |
| Backend / API REST | **Fastify** | TS-first, validação por schema, plugins por funcionalidade, OpenAPI integrado |
| Contratos | **Zod + OpenAPI/Swagger** | Um schema gera validação, tipos e documentação |
| Banco | **PostgreSQL** | Domínio fortemente relacional |
| ORM | **Prisma** | Schema declarativo, migrations versionadas, cliente tipado |
| Auth | **argon2id + JWT (access/refresh) + RBAC** | Mapeia as personas Visitante/Jogador/Administrador |
| Frontend | **React + Vite + TS** (+ React Router, TanStack Query, Tailwind + shadcn/ui) | Ecossistema maduro e integração com API REST |
| Testes | **Vitest + Supertest + Playwright** | Unidade, integração de API e end-to-end |
| Lint/formatação | **ESLint + Prettier** | Maturidade e amplitude de plugins |
| Infra/CI | **Docker Compose + GitHub Actions** | Padroniza ambiente e verifica PRs |
| Organização | **Monorepo com npm workspaces** + `packages/shared` | Compartilha schemas/tipos |

O documento traz, para cada item, justificativa e as **alternativas consideradas** (Express,
NestJS, MySQL/MariaDB, NoSQL, Drizzle, bcrypt, Next.js, Biome, sessão em servidor), além de uma
estrutura de repositório sugerida. É documentação apenas — sem código.

## Copilot

O arquivo `.sdd/task.md` já existia vazio. Perguntei o escopo desejado.

> Escolha do usuário: "Backlog geral de tarefas de todo o projeto, organizado pelas etapas do plan.md (Recomendado)"

Criei `.sdd/task.md` como backlog geral de tarefas, derivado do `plan.md` e organizado pelas
mesmas etapas:

- **Como usar** — identificadores (`T<etapa>.<n>` para tarefas, `F<n>` para funcionalidades), legenda de status (`[ ]`, `[~]`, `[x]`, `[!]`) e a regra SDD de não implementar antes da SPEC.
- **Ciclo padrão por funcionalidade** — *Escrever SPEC → Implementar → Testar*.
- **Etapas 0 a 7** — tarefas em checklist: Etapa 0 (Fundação) com 12 tarefas técnicas; Etapas 1 a 6 com as funcionalidades F1–F15 em seu ciclo; Etapa 7 (Consolidação) com 5 tarefas.
- **Tarefas transversais (TC.01–TC.05)** — contínuas, incluindo o registro de sessões em `prompts/sessoes/`.
- **Critérios de conclusão de etapa** — SPEC escrita, implementação em `src/` e testes passando em `tests/`.

Total: **69 tarefas** em checklist. O backlog não entra em requisitos funcionais nem em código.

## Usuário

depois de ter criado o .sdd/task.md, crie SPEC de arquitetura para a Etapa 0.

A estrutura da SPEC ter:

# O que e Por quẽ
# Critério de aceite
# Fora do Escopo

A SPEC deve:

- consolidar as tecnologias e ferramentas escolhidas;
- registrar as justificativas das principais decisões;
- registrar as alternativas consideradas quando elas estiverem presentes na proposta;
- definir a arquitetura geral do sistema;
- manter alinhamento com a visão_geral.md;
- servir como referência para as próximas SPECs e para a implementação.

Não crie ainda as SPECS funcionais, como cadastro, login ou catálogo.

Ao final, apresente:

1. o conteúdo criado em .sdd/task.md;
2. o conteúdo da SPEC de arquitetura;
3. uma breve explicação de como a Etapa 0 se relaciona com as próximas etapas do SDD.

## Copilot

Criei a SPEC de arquitetura em `SPEC/arquitetura.md` (convenção do projeto: SPECs em `SPEC/`),
usando a estrutura solicitada — `# O que e Por quê`, `# Critério de aceite` e
`# Fora do Escopo`.

Conteúdo da SPEC:

- **O que e Por quê** — contexto e objetivos da SPEC da Etapa 0; seção de alinhamento com a visão geral (tabela "definição da visão geral → como a SPEC atende"); **tabela de decisões consolidadas** com camada/decisão/justificativa/alternativas consideradas; **arquitetura geral** com diagrama cliente-servidor em camadas, responsabilidades das camadas, aspectos transversais (auth/RBAC, validação, erros, logging pino, config), convenções de API REST (versionamento `/api/v1`, JSON, OpenAPI), estrutura de repositório e ambientes (dev local com Docker Compose e CI).
- **Critério de aceite** — 13 itens verificáveis (estrutura de pastas, TypeScript `strict`, banco/migrations, endpoint de saúde, validação Zod/OpenAPI, frontend consumindo a API, lint/format, testes configurados, CI verde, convenções Git/GitHub, `.env`/`.env.example`, template de SPEC e padrão de sessões, alinhamento com a visão geral).
- **Fora do Escopo** — SPECs funcionais F1–F15, requisitos funcionais detalhados, modelo de dados por funcionalidade, implementação, design visual, algoritmo de recomendações e provedores de deploy em produção.

Na mesma resposta, apresentei os três itens pedidos: o conteúdo integral de `.sdd/task.md`, o
conteúdo da SPEC de arquitetura e a explicação de que a Etapa 0 é o **contrato técnico
transversal** que as SPECs funcionais referenciam (sem redefinir stack, padrões de API,
autenticação ou organização de pastas), e cujos critérios de aceite liberam o início das
etapas seguintes na ordem `0 → 1 → 2 → …`.
