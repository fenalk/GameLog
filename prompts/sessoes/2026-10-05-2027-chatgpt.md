# Visão Geral do GameLog

## O quê e por quê

GameLog é uma plataforma web de catálogo e avaliação de jogos. A ideia é ser uma mistura de catálogo de jogos, diário de jogos e avaliações sociais.

O sistema permitirá que os usuários descubram jogos, registrem os jogos que já jogaram, avaliem e escrevam resenhas, criem listas e acompanhem outros jogadores.

O GameLog terá três tipos de usuários: **Visitante, Jogador e Administrador**.

## Problema

Jogadores muitas vezes perdem o histórico dos jogos que já jogaram e não possuem um lugar simples para organizar esse histórico e descobrir novos jogos a partir das opiniões de outras pessoas.

## Solução

O GameLog oferecerá uma plataforma centralizada para descoberta, organização e avaliação de jogos.

Os visitantes poderão consultar o catálogo e visualizar informações e avaliações dos jogos. Jogadores cadastrados poderão manter seu histórico de jogos, avaliar e resenhar jogos, criar listas e seguir outros usuários. Administradores serão responsáveis pelo gerenciamento do catálogo e pela moderação do conteúdo.


Isso deixa o projeto **mais alinhado com a ideia de SDD**, porque as specs ficam pequenas, implementáveis e fáceis de relacionar aos commits.

Por exemplo:


pode conter:

```text

RF-002 — O sistema deve exigir nome, e-mail e senha.

RF-003 — O sistema não deve permitir e-mails duplicados.

## Critérios de aceitação

CA-002 — Dado um e-mail já cadastrado,
o sistema deve rejeitar o cadastro.
```

**`src/`**
É o código da aplicação.

**`Tests/`**
Contém os testes automatizados relacionados às funcionalidades implementadas.

**`Prompts/sessoes/`**
É onde você pode guardar os prompts utilizados durante o desenvolvimento com IA e o registro das sessões, algo especialmente interessante para uma atividade de **Desenvolvimento de Software Apoiado por IA**.

### Uma coisa importante sobre as 15 specs

Eu **não faria necessariamente uma spec para cada módulo**.

Por exemplo, `auth` pode gerar várias specs:

```text

├── 002-login.md
├── 003-logout.md
├── 004-recuperacao-senha.md
└── ...
```

E todas elas podem implementar partes de:

```text
src/modules/auth/
```

Isso é melhor para o SDD porque as specs ficam **pequenas e específicas**.

A estrutura final poderia, portanto, crescer naturalmente:

```text

```

em vez de tentar colocar toda a funcionalidade de um módulo enorme dentro de uma única spec.

```text
   ↓

   ↓
```

### O que significa `AAAA-MM-DD-HHMM-<ferramenta>`

É um padrão para o nome do arquivo:

```text
AAAA = ano
MM   = mês
DD   = dia
HH   = hora
MM   = minuto
```

Então:

```text
2026-10-05-2322-chatgpt.md
```

significa:

> **05/10/2026 às 23:22 — ChatGPT**

Se você usar outro agente, poderia ser:

```text
2026-10-06-1015-claude.md
2026-10-06-1430-gemini.md
```

### E como isso se relaciona com as SPECs?

É importante separar as coisas:

```text
GameLog/
│
├── README.md
│
├── SPEC/
│   ├── 001-cadastro.md
│   ├── 002-login.md
│   └── ...
│
├── src/
│   └── ...
│
├── Tests/
│   └── ...
│
└── Prompts/
    └── sessoes/
        ├── 2026-10-05-1900-chatgpt.md
        ├── 2026-10-05-2322-chatgpt.md
        └── ...
```

**`SPEC/`** → especificações que orientam o desenvolvimento.

**`src/`** → código produzido.

**`Tests/`** → testes.

**`Prompts/sessoes/`** → histórico das conversas com os agentes de IA.

Portanto, **não é para criar uma sessão dentro de cada módulo**. Você registra a conversa inteira que teve com o agente naquela sessão.

E, pelo texto que você trouxe, **“diálogo completo” significa guardar tanto suas mensagens quanto as respostas da IA**, não apenas o prompt que você enviou.
